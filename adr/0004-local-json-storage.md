# Хранить настройки и кэш в файлах JSON с атомарной записью

## Контекст и постановка задачи

Приложение должно сохранять между запусками настройки (последний город, избранное, единицу давления) и прогнозы для последних 10 городов, чтобы показывать их без сети (REQ-INT-009). Ограничение CON-5 предпочитает локальные файлы JSON и не допускает базу данных. Файлы могут быть повреждены вручную или при сбое, и приложение при этом не должно падать (REQ-REL-001). Приложение поставляется ZIP-архивом без установщика (REQ-INST-001).

Как хранить настройки и кэш?

## Драйверы решения

* Соответствие CON-5 и REQ-INT-009
* Устойчивость к повреждению файлов (REQ-REL-001)
* Простота: без установки компонентов и прав администратора (REQ-INST-001)
* Читаемость и возможность проверить содержимое текстовым редактором
* Тестируемость через интерфейс `IStorage` (REQ-MAINT-002)

## Рассмотренные варианты

* Файлы JSON с атомарной записью
* SQLite
* Пользовательские настройки .NET или реестр Windows

## Итог решения

Выбранный вариант: «Файлы JSON с атомарной записью», потому что он соответствует CON-5, не требует дополнительных компонентов и позволяет простыми средствами реализовать восстановление после повреждения.

### Последствия

* Хорошо, потому что файлы `settings.json` и `cache.json` в `%AppData%/WeatherDesk` читаются человеком и открываются в текстовом редакторе
* Хорошо, потому что запись во временный файл с последующей заменой исключает полупустой файл при сбое
* Хорошо, потому что `IStorage` легко подменяется в тестах
* Плохо, потому что нет запросов и индексов: поиск по кэшу выполняется в памяти (допустимо при 10 записях)
* Плохо, потому что при росте объёма данных (например, истории) решение придётся пересмотреть
* Требуется версия схемы `schemaVersion` в каждом файле для будущих миграций

### Подтверждение

* Модульные тесты `JsonFileStorage`: чтение, запись, пустой файл, содержимое `{{{`, отсутствующий файл (повреждённый файл переименовывается в `.bad`, приложение стартует со значениями по умолчанию)
* Тест устойчивости: прерывание записи не оставляет повреждённого основного файла
* Инспекция: кодировка UTF-8, каталог `%AppData%/WeatherDesk`

## Плюсы и минусы вариантов

### Файлы JSON с атомарной записью

* Хорошо, потому что соответствует CON-5
* Хорошо, потому что нет внешних зависимостей, кроме `System.Text.Json`
* Хорошо, потому что просто восстанавливать после повреждения
* Нейтрально, потому что при 10 городах размер кэша невелик
* Плохо, потому что нет транзакций между двумя файлами

### SQLite

Встраиваемая реляционная база данных в одном файле.

* Хорошо, потому что транзакции и запросы
* Плохо, потому что CON-5 не предполагает использование базы данных
* Плохо, потому что добавляет зависимость и нативные библиотеки в поставку, что усложняет проверку лицензий (REQ-COMP-002)
* Плохо, потому что избыточно для 10 записей кэша и нескольких настроек

### Пользовательские настройки .NET или реестр Windows

* Хорошо, потому что простой доступ к настройкам
* Плохо, потому что кэш прогнозов сюда не подходит из-за размера
* Плохо, потому что данные нельзя посмотреть и поправить в текстовом редакторе, а реестр остаётся после удаления папки, что противоречит REQ-INST-001 («удаление удалением папки»)

## Дополнительная информация

Срок хранения кэша по умолчанию 24 часа (OQ-7); записи старше этого срока не показываются и удаляются при чтении. Ключ записи кэша: координаты, округлённые до двух знаков. Давление в кэше хранится в гПа (ADR-0003). Связанные решения: ADR-0002. Затронутые требования SRS: CON-5, REQ-INT-009, REQ-REL-001, REQ-INST-001. Представления SDD: 007-information, 014-concurrency.
