# Объединять три источника данных составным провайдером с параллельным опросом

## Контекст и постановка задачи

Заказчик требует, чтобы данные поступали через три внешних API (C-2). Приложение показывает усреднённые значения, число ответивших источников и разброс (SRS 1.2), а при недоступности части сервисов продолжает работать по остальным (SRS 2.1). Источники различаются форматами: у Met Norway время в UTC, шаг прогноза меняется с часового на шестичасовой, нет минимума и максимума за день. Время ответа не должно превышать 3 секунды для 95% запросов (REQ-PERF-001), а замена источника не должна менять код ViewModel и окна (REQ-MAINT-003).

Как организовать получение и объединение данных трёх источников?

## Драйверы решения

* Устойчивость к сбою отдельных источников (отказ одного не должен ломать экран)
* Время отклика: источники должны опрашиваться параллельно (REQ-PERF-001)
* Замена и добавление источников без изменения интерфейса (REQ-MAINT-003)
* Тестируемость на заранее подготовленных ответах (REQ-MAINT-002)
* Ограничение CON-3: без собственного серверного компонента

## Рассмотренные варианты

* Составной провайдер (`AggregatingWeatherProvider`)
* Последовательный опрос с резервным источником
* Объединение данных в `WeatherService` или ViewModel

## Итог решения

Выбранный вариант: «Составной провайдер», потому что `AggregatingWeatherProvider` сам реализует `IWeatherProvider`, поэтому слои выше видят три источника как один, опрос идёт параллельно, а сбой отдельного источника превращается в запись о статусе, а не в ошибку всей загрузки.

### Последствия

* Хорошо, потому что общее время ответа определяется самым медленным источником, а не суммой
* Хорошо, потому что новый источник подключается регистрацией ещё одной реализации `IWeatherProvider`
* Хорошо, потому что агрегатор тестируется с поддельными провайдерами без сети
* Плохо, потому что нужно приводить форматы всех источников к единой модели; это основная часть трудоёмкости подключения трёх источников
* Плохо, потому что для данных, которых у части источников нет (например, часовые значения Met Norway далеко вперёд), число источников меняется от точки к точке
* Требуется ограничение частоты запросов по каждому хосту (REQ-REL-003)

### Подтверждение

* Модульные тесты агрегатора с поддельными провайдерами: все ответили, один не ответил, ни один не ответил, у одного значения `null`
* Демонстрация REQ-MAINT-003: подмена `OpenMeteoClient` тестовой реализацией без изменения интерфейса
* Тест на таймауты: источник с задержкой более 10 секунд не задерживает результат остальных

## Плюсы и минусы вариантов

### Составной провайдер

Агрегатор принимает список `IWeatherProvider`, опрашивает их через `Task.WhenAll` с индивидуальным таймаутом и объединяет результаты по правилам усреднения.

* Хорошо, потому что единый интерфейс для всех слоёв выше
* Хорошо, потому что параллельный опрос и изоляция сбоев
* Хорошо, потому что легко расширять и тестировать
* Нейтрально, потому что добавляется один дополнительный класс
* Плохо, потому что правила усреднения надо проектировать и тестировать отдельно

### Последовательный опрос с резервным источником

Основной источник опрашивается первым, остальные используются только при его сбое; значения не усредняются.

* Хорошо, потому что проще реализация
* Плохо, потому что противоречит описанию из SRS: усреднение по трём источникам и показ разброса
* Плохо, потому что при последовательном опросе время ответа суммируется

### Объединение данных в WeatherService или ViewModel

Логика объединения находится в сервисе или ViewModel, которые обращаются к каждому клиенту напрямую.

* Хорошо, потому что меньше классов
* Плохо, потому что ViewModel узнаёт о числе и составе источников, что нарушает REQ-MAINT-003
* Плохо, потому что логика объединения трудно тестируется вместе с кэшем и состояниями экрана

## Дополнительная информация

В тексте SRS отсутствуют описания REQ-INT-010, REQ-FUNC-020 … REQ-FUNC-022, REQ-REL-005 и OQ-10, поэтому правила усреднения приняты по описанию из разделов 1.2 и 2.1 SRS и зафиксированы в представлении 011-algorithm-aggregation SDD; их нужно перенести в SRS v0.2. Состав источников: Open-Meteo (best match), Open-Meteo с моделью ECMWF, Met Norway; Met Norway требует заголовок `User-Agent` с контактом разработчика (CON-8). Решение стоит пересмотреть, если один из сервисов перестанет быть бесплатным или изменит условия использования. Связанные решения: ADR-0003, ADR-0005. Представления SDD: 002-composition, 005-structure, 009-interaction-load, 011-algorithm-aggregation, 014-concurrency.
