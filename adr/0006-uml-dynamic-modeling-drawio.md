# Моделировать динамическое поведение на UML в draw.io и связывать диаграммы трассировкой

## Контекст и постановка задачи

Для WeatherDesk нужна модель динамического поведения: варианты использования, активность, состояния и взаимодействие компонентов. Модель должна быть связана с SRS и SDD, храниться в репозитории рядом с документами и изменяться вместе с ними. В SDD уже есть диаграммы Mermaid для структуры (контекст, композиция, зависимости, развёртывание), но Mermaid не рисует диаграмму вариантов использования и не поддерживает нотацию UML для активности, а в диаграмме последовательности ограничен в `ref`, создании и уничтожении участников.

Какими средствами рисовать UML-диаграммы, какой набор диаграмм взять и как связать их между собой и с требованиями?

## Драйверы решения

* Четыре типа UML: варианты использования, активности, состояния, последовательности
* Нотация, близкая к стандартной UML: `include`/`extend`, развилки и слияния, составные состояния и история, `create`/`destroy`, `par`/`alt`/`ref`, ограничение длительности, gates
* Хранение в git: файл должен открываться без платных программ и не быть бинарным
* Возможность править диаграмму мышью и сразу видеть результат
* Прослеживаемость диаграмм к требованиям SRS и элементам SDD
* Отсутствие платных инструментов и серверных компонентов (CON-6)

## Рассмотренные варианты

* draw.io (diagrams.net) с хранением `.drawio` и экспортом PNG
* PlantUML (диаграммы как код)
* Mermaid
* Microsoft Visio

## Итог решения

Выбранный вариант: «draw.io», потому что он бесплатен, рисует все необходимые элементы UML, а файл `.drawio` — обычный XML, который хранится в git; изображения PNG экспортируются из того же файла и подключаются в SDD и отчёт.

Исходники лежат в `uml/src`, экспортированные PNG — в `uml/img` под тем же именем. Диаграммы структуры в SDD остаются в Mermaid, потому что GitHub рисует их без дополнительных шагов.

### Механизм построения и связи диаграмм

Диаграммы строятся последовательно, и каждая следующая уточняет предыдущую:

1. **Варианты использования** выводятся из требований SRS. Актёры (Пользователь, Таймер, Погодные сервисы, Сервис геокодинга) находятся вне границы системы; прецеденты инициируются актёром; между прецедентами используются только `include` (UC-03 входит в UC-02, UC-04 и UC-05) и `extend` (UC-09 расширяет UC-08, UC-12 расширяет UC-03). Потоки событий хранятся в `uml/use-cases.md`.
2. **Активность** детализирует поток событий прецедентов UC-02, UC-03 и UC-12: действия, решения и слияния, параллельный опрос трёх источников (развилка и соединение), примечания и конечный узел.
3. **Состояния** описывают жизненный цикл ключевой сущности, которая появляется в потоках прецедентов — экрана прогноза: составные состояния «Показ данных» и «Ошибка», история `H`, события, условия и действия входа.
4. **Последовательность** показывает, какие компоненты SDD обмениваются сообщениями при выполнении прецедента: синхронные и асинхронные сообщения, возвраты, создание и уничтожение объекта, фрагменты `par`, `alt`, `ref`, ограничение длительности и точки входа и выхода.

| Прецедент | Активность | Состояния | Последовательность | Требования SRS / SYS |
|-----------|------------|-----------|--------------------|----------------------|
| UC-02 Выбрать город и получить прогноз | Загрузка прогноза | Loading → Показ данных | LoadForecast | REQ-FUNC-002…004, REQ-REL-004; SYS-FUNC-003, 013 |
| UC-03 Получить и объединить данные | Загрузка прогноза (развилка) | Ready, ReadyPartial | LoadForecast (`par`, `create`, `destroy`) | REQ-INT-007, REQ-INT-010; SYS-FUNC-004…006 |
| UC-04, UC-05 Обновление | Загрузка прогноза | Показ данных → Loading | LoadForecast | REQ-FUNC-014, 015; SYS-FUNC-011 |
| UC-12 Показать ошибку или кэш | Загрузка прогноза (ветки «нет ответа») | Ошибка, OfflineCached | LoadForecast (`ref`) | REQ-INT-005, REQ-FUNC-017; SYS-FUNC-012, 019 |
| UC-01 Найти город | — | CityNotFound | — | REQ-FUNC-001, REQ-INT-008; SYS-FUNC-002 |

Идентификаторы `UC`, `REQ` и `SYS` на диаграммах и в документах совпадают. Представления SDD: вариантов использования — 019, активности — 020, последовательности — 009, состояний — 013.

### Последствия

* Хорошо, потому что нотация близка к стандартной UML и совпадает с требованиями задания
* Хорошо, потому что диаграмму можно править мышью, а файл остаётся текстом и сравнивается в git (хотя XML менее читаем, чем код PlantUML)
* Хорошо, потому что цепочка прецедент → активность → состояния → последовательность делает модель проверяемой на согласованность
* Плохо, потому что PNG нужно экспортировать заново после каждой правки `.drawio`
* Плохо, потому что в SDD теперь два формата диаграмм (draw.io и Mermaid)
* Плохо, потому что метки на рёбрах в draw.io привязаны к координатам и при крупных правках могут потребовать ручной перестановки

### Подтверждение

* Каждый файл `.drawio` открывается в draw.io без ошибок, и для него в `uml/img` есть актуальный PNG (проверка при code review)
* Идентификаторы `UC`, `REQ` и `SYS` на диаграммах совпадают с `uml/use-cases.md` и SDD
* Каждый прецедент из таблицы трассировки имеет описание с пояснением, предусловиями, потоками и постусловиями

## Плюсы и минусы вариантов

### draw.io

* Хорошо, потому что бесплатен, работает в браузере и как настольная программа
* Хорошо, потому что поддерживает наборы элементов UML (актёры, фреймы, состояния, активации)
* Хорошо, потому что `.drawio` — XML и хранится в git
* Нейтрально, потому что раскладка выполняется вручную
* Плохо, потому что различия между версиями читаются хуже, чем у текстового кода

### PlantUML

* Хорошо, потому что поддерживает все нужные типы диаграмм и нотацию UML
* Хорошо, потому что текст легко сравнивать в git
* Нейтрально, потому что нужен Java или онлайн-сервис для рендеринга
* Плохо, потому что раскладку диаграммы задаёт программа, и вручную её не поправить; GitHub не отображает PlantUML без экспорта

### Mermaid

* Хорошо, потому что GitHub рисует диаграммы без дополнительных шагов
* Плохо, потому что нет диаграммы вариантов использования
* Плохо, потому что активность выражается блок-схемой, а не нотацией UML, а для последовательности ограничены `ref`, создание и уничтожение участников

### Microsoft Visio

* Хорошо, потому что богатый набор шаблонов UML
* Плохо, потому что формат `.vsdx` бинарный и плохо сравнивается в git
* Плохо, потому что программа платная и недоступна на всех компьютерах
